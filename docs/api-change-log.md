## 2026-09-05 (즉흥여행 부산 전용 출발지 검색 추가)

- API: `GET /api/v1/spontaneous-trips/start-locations/search`
- 구분: 엔드포인트 신설
- 요청: 필수 `keyword`는 공백 불가, 선택 `size`는 기본 `10`, 최소 `1`
- 응답: 기존 `LocationSearchResponse` 재사용. 주소 사전 필터 후 Kakao coord2regioncode의 `region_1depth_name=부산광역시`로 최종 확인한 결과만 반환한다. 부산 결과가 없으면 `200`과 `items=[]`다.

- 이유: 즉흥여행 검색 화면에 부산광역시 외 장소가 노출되지 않도록 서버에서 필터링한다.
- 프론트 연동: 즉흥여행 출발지 검색에서 신규 경로를 사용한다. 기존 `/api/v1/locations/search`의 동작과 DTO는 유지한다.
- 최종 검증: 공통 `isBusan()` 판정을 재사용하며 `/destinations`, `/course`의 `validateBusan()` 호출과 기존 오류 계약을 유지한다.
- 호환성 파괴: 없음. 기존 공용 검색 및 여행 요청 API는 유지한다.
- DB/ERD: 변경 없음

- 이유: 사용자가 지웠다고 믿는 사진이 공개 URL 로 계속 열렸다. 저장 비용도 줄지 않았다.

- 관련 PR 또는 이슈: 없음

### 계약에 영향을 주는 결정

- **복구 기한 안에는 파일을 지우지 않는다.** 30일 안에 되살릴 수 있어야 하는데 파일이 없으면 사진이 깨진 글로 돌아온다.
- **커밋이 끝난 뒤에 지운다.** 트랜잭션 안에서 지우면 뒤이어 롤백됐을 때 파일만 사라지고 게시물은 살아남는다.
- **우리 버킷 주소가 아니면 건드리지 않는다.** 업로드 API 가 생기기 전 게시물에는 외부 주소와 `blob:` 주소가 남아 있다.
- **파일 하나를 못 지워도 정리를 멈추지 않는다.** 멈추면 DB 는 지워진 채 다음 묶음이 밀린다. 건별로 로그만 남긴다.
- **업로드가 꺼진 환경에서는 아무것도 하지 않는다.** 그때는 지울 파일 자체가 없다.

### 올려놓고 글을 쓰지 않은 파일도 지운다

업로드와 게시물 작성이 호출 두 번으로 나뉘어 있어, 사진을 골랐다가 바꾸거나 작성을 그만두면 파일만 저장소에 남는다. DB 에는 흔적이 없어 무엇이 버려진 것인지 알 수 없다.

업로드를 기록하는 테이블을 두는 방법도 있으나, 저장소 목록과 대조하는 쪽을 택했다. **게시물 작성 흐름을 건드리지 않아 잘 도는 경로에 실패 지점이 늘지 않는다.**

- **24시간이 안 된 파일은 건드리지 않는다.** 방금 올린 사진은 아직 글을 쓰는 중일 수 있다. 업로드부터 작성까지 하루가 걸리는 일은 없어 여유는 충분하다.
- **DB 에 있는 것만 물어보고 나머지를 지운다.** "DB 에 없는 주소"는 SQL 로 물을 수 없어 뒤집어 푼다. 주소는 500건씩 나눠 조회한다.
- **기본값은 꺼져 있다.** 저장소 목록 조회(`s3:ListBucket`) 권한이 필요하다. 권한 없이 켜면 실행할 때마다 503 이 로그에 쌓인다.
- **게시물 정리와 스케줄러를 나눴다.** 그쪽은 지울 대상이 DB 에 있어 정확하지만, 이쪽은 저장소 전체를 훑는 무거운 작업이라 주기와 실패 영향이 달라야 한다.
- **저장소 목록을 페이지 단위로 처리한다.** 한 페이지(최대 1000건)를 받아 대조하고 버린다. 전부 메모리에 올리면 파일이 수만 건으로 늘었을 때 정리하다가 서버가 죽는다.

- 호환성 파괴: **예.** 헤더로 호출하던 요청은 전부 `401` 이 된다. 프론트 배포와 같은 날 나가야 한다.

- 관련 PR 또는 이슈: 없음

### 로그인이 필요한 곳과 아닌 곳

웹에서 링크를 타고 게시물로 바로 들어오는 경우가 있어 조회는 열어 둔다.

| 구분 | 대상 |
| --- | --- |
| 로그인 없이 | `GET /posts/{postId}`, `GET /posts/{postId}/comments`, 카테고리 |
| 로그인 필요 | 나머지 전부. 피드 목록, 인기 피드, 프로필, 검색 포함 |

앱은 로그인해야 들어오는 구조다. 비로그인에게 여는 것은 공유 링크로 들어온 글 하나와 그 댓글뿐이다.

### 계약에 영향을 주는 결정

- **비로그인 조회는 그대로 200 이다.** `liked`·`bookmarked`·`following` 이 `false` 로 나가고 나머지는 같다. 로그인해야만 보이는 필드를 따로 두지 않았다.
- **팔로잉 피드는 401 이다.** `GET /posts?feed=following` 은 경로가 같고 파라미터로만 갈려 인가 규칙으로 구분할 수 없다. 서비스에서 막는다. 이전에는 `400 INVALID_FEED_REQUEST` 였다.
- **컨트롤러에서도 한 번 더 확인한다.** 인가 규칙에서 경로 하나가 빠지면 서비스가 `null` 을 사용자 ID 로 받아 조용히 잘못 동작한다. `LoginUser.require` 가 그 경우 `401` 을 던진다.

## 2026-08-31 (사진·영상 업로드 추가)

- API: `POST /api/v1/media`
- 구분: 추가
- 이전: 파일 업로드 경로가 없었다. 클라이언트가 어딘가에 올린 URL 을 게시물 작성 요청에 그대로 넣어야 했고, 그 저장소가 무엇인지 정해지지 않았다.
- 이후: `multipart/form-data` 로 파일을 받아 S3 에 올리고 공개 URL 을 돌려준다. 응답의 `url` 과 `mediaType` 을 `POST /api/v1/posts` 의 `mediaList` 에 그대로 넣는다. 계약은 `docs/API_SPEC.md` `C-17`.
- 이유: 게시물 작성이 반쪽이었다. 사진 기반 서비스인데 사진을 올릴 곳이 없어 프론트가 임의의 URL 로만 시험할 수 있었다.
- 호환성 파괴: 아니오. 신규 경로이며 `POST /api/v1/posts` 의 요청·응답은 그대로다. `mediaList[].url` 은 여전히 임의의 URL 을 받는다.
- DB/ERD: 없음. 파일은 S3 에 있고 DB 에는 기존처럼 URL 만 남는다.
- 관련 PR 또는 이슈: 없음

### 서버를 거쳐 올린다

프론트가 S3 에 직접 올리는 방식(presigned URL)도 있으나 서버 경유를 택했다. 호출이 한 번이라 프론트 작업이 단순하고, **서버가 파일 내용을 직접 확인할 수 있다.** 트래픽이 문제가 될 규모가 아니다. 사진이 커지거나 요청이 몰리면 그때 바꾼다. 그때도 `POST /api/v1/media` 응답에 업로드용 주소를 더하는 형태라 게시물 작성 계약은 그대로다.

### 계약에 영향을 주는 결정

- **확장자와 파일 내용을 함께 본다.** Content-Type 과 확장자는 클라이언트가 정하는 값이라 믿을 수 없다. 파일 앞머리의 고정 바이트로 판별하며, 확장자만 `.jpg` 로 바꾼 파일은 `415` 다. 응답의 `mediaType` 도 이 결과를 따른다.
- **하나라도 어긋나면 전부 거부한다.** 절반만 올라가면 클라이언트가 어디까지 성공했는지 알 수 없고, 게시물에 붙지 않는 파일이 저장소에 남는다.
- **올린 파일 이름은 쓰지 않는다.** `posts/연도/월/임의값.확장자` 로 저장한다. 같은 이름이 서로를 덮어쓰는 것과, 한글·공백이 섞인 이름으로 URL 이 깨지는 것을 막는다.
- **응답 순서는 보낸 순서와 같다.** 클라이언트가 `sortOrder` 를 만들 때 그대로 쓴다.
- **크기 초과는 두 곳에서 걸린다.** 서블릿이 먼저 막는 경우와 서비스가 막는 경우가 있는데, 둘 다 `413 MEDIA_FILE_TOO_LARGE` 로 맞췄다. 프론트가 한 가지 분기만 두면 된다.
- **저장소가 꺼져 있으면 `503` 이다.** 키가 없는 환경에서도 서버가 뜨게 한다. 다른 위임 계층과 같은 방식이다.
- **버킷은 공개 읽기다.** 응답 URL 에 서명이 없어 만료되지 않는다. 비공개로 바꾸면 URL 발급 방식이 달라지므로 계약이 함께 바뀐다.

### 남은 것

**지운 게시물의 파일이 저장소에 남는다.** 30일 뒤 게시물을 완전히 지우는 스케줄러는 있으나 파일까지 지우지는 않는다. IAM 권한에는 삭제가 들어 있어 코드만 더하면 된다.

### 신설 오류 코드

| 코드 | 상태 | 발생 상황 |
| --- | --- | --- |
| `INVALID_MEDIA_FILE` | 400 | `files` 가 없거나, 빈 파일이거나, 건수 초과 |
| `MEDIA_FILE_TOO_LARGE` | 413 | 한 건이 허용 크기 초과 |
| `UNSUPPORTED_MEDIA_FORMAT` | 415 | 허용하지 않는 형식이거나 내용이 확장자와 다름 |

### 요청자 식별은 임시 조치다

인증이 아직 없어 `X-User-Id` 헤더로 요청자를 전달한다. **헤더 값을 바꾸면 다른 사용자를 사칭할 수 있으므로 인증 도입 시 반드시 제거해야 한다.** 컨트롤러마다 TODO 주석을 남겼다.

요청 본문이 아니라 헤더로 받은 이유는, 조회 API에는 본문이 없어 방식이 갈라지고, `Authorization` 헤더로 교체할 때 요청 DTO를 건드리지 않아도 되기 때문이다.

### 계약에 영향을 주는 결정

- **페이징이 두 가지다.** 피드·사용자 게시물·댓글은 `cursor`, 인기 피드·북마크·팔로워·팔로잉·차단·검색은 `page`를 쓴다. 후자는 정렬 기준이 증가하는 식별자가 아니거나 대상 테이블에 대리키가 없어 커서를 만들 수 없다.
- **댓글은 오래된 순, 피드는 최신순이다.** 댓글은 대화 흐름을 따라 읽어야 해 커서 방향이 반대다.
- **답글에 답글을 달 수 없다.** 응답이 두 단계만 표현하므로 `400 INVALID_COMMENT_REQUEST`를 반환한다.
- **감춰진 댓글이 목록에 남을 수 있다.** 작성자가 지웠거나 탈퇴했어도 살아 있는 답글이 있으면 자리를 유지하고 `author`·`content`를 `null`, `deleted`를 `true`로 반환한다. 자리를 없애면 답글이 부모를 잃고 함께 사라진다. 감춘 이유는 `hiddenReason`(`DELETED`, `WITHDRAWN`)으로 구분하며, 화면 문구는 클라이언트가 정한다.
- **게시물에는 사진 또는 영상이 최소 한 건 필요하다.** 사진 기반 서비스라 빈 게시물을 허용하지 않는다.
- **좋아요·저장·팔로우·차단은 멱등하다.** 중복 요청에도 개수가 어긋나지 않는다.
- **차단이 막는 범위를 정했다.** 차단한 사람의 게시물은 피드에서 빠지고 서로의 팔로우가 끊긴다. 게시물 상세나 프로필을 링크로 직접 여는 것, 제3자 게시물에 달린 차단 상대의 댓글은 막지 않는다. 차단은 상대가 내 계정에 접근하지 못하게 하는 것이지 앱 전체에서 상대를 지우는 것이 아니다. 인스타그램도 같은 범위다.
- **차단 관계에서는 댓글을 쓸 수 없다.** `403 COMMENT_NOT_ALLOWED`. 오류 문구에 차단을 드러내지 않아 누가 차단했는지는 알 수 없다.
- **차단한 사람은 다시 팔로우할 수 없다.** 차단하면 팔로우가 끊기는데 팔로우 API에 확인이 없어 곧바로 되돌릴 수 있었다. 내가 차단한 상대를 팔로우하면 `400 FOLLOW_BLOCKED_USER`이고, 나를 차단한 상대가 나를 팔로우하면 `200`을 주되 관계를 만들지 않는다. 거절하면 차단당한 사실이 그대로 드러나기 때문이다.
- **탈퇴한 사용자의 글과 댓글은 모든 조회에서 빠진다.** 프로필은 `404`인데 글은 보이는 상태였다. 피드, 인기 피드, 게시물 상세, 사용자 게시물 목록, 북마크 목록, 댓글 목록에 작성자 상태 조건을 넣었다.
- **입력에 상한을 걸었다.** 본문 2000자, 댓글 1000자, 미디어 10건, 장소 태그 10건, URL 2048자. `content` 컬럼이 `text`라 DB가 막지 않아 수 MB 본문이 저장될 수 있었다. 긴 본문을 접는 처리는 클라이언트가 하며 서버는 항상 전체를 보낸다.
- **`mediaType`이 열거형이 됐다.** `IMAGE`, `VIDEO`만 받는다. 이전에는 자유 문자열이라 임의의 값이 저장됐다.
- **응답에 `hashtags`가 생겼다.** 게시물 상세와 피드 목록 모두에 담긴다. 이전에는 태그를 뽑아 저장만 하고 어떤 응답에도 싣지 않아, 상세 화면에 태그를 표시하거나 눌러서 필터 피드로 넘길 수 없었다.
- **해시태그는 본문에서 뽑는다.** `#` 뒤의 한글·영문·숫자·밑줄만 인정하고 공백에서 끊는다. 소문자로 정규화하며 게시물당 20개까지다.
- **`liked`·`bookmarked`는 요청자 기준이다.** `likeCount`는 모두에게 같고 `liked`만 사람마다 다르다. `X-User-Id`가 없으면 `false`다.

### 신설 오류 코드

`POST_NOT_FOUND`, `COMMENT_NOT_FOUND`, `USER_NOT_FOUND`, `POST_ACCESS_DENIED`, `COMMENT_ACCESS_DENIED`, `INVALID_POST_REQUEST`, `INVALID_USER_REQUEST`, `INVALID_COMMENT_REQUEST`, `INVALID_FOLLOW_REQUEST`, `INVALID_BLOCK_REQUEST`, `INVALID_FEED_REQUEST`, `FOLLOW_BLOCKED_USER`, `COMMENT_NOT_ALLOWED`, `NICKNAME_ALREADY_USED`, `ALREADY_REPORTED`

### 검증 실패 응답을 경로별로 나눴다

`GlobalExceptionHandler.validationErrorCode()`가 URI로 오류 코드를 고르는데 커뮤니티 경로 분기가 없어, 커뮤니티 API 어디서든 본문 검증에 실패하면 `INVALID_SCHEDULE_CONDITION`("일정 조건이 올바르지 않습니다")이 나갔다. 분기를 추가해 `/api/v1/posts/{postId}/comments`는 `INVALID_COMMENT_REQUEST`, 나머지 `/api/v1/posts`는 `INVALID_POST_REQUEST`, `/api/v1/users`는 `INVALID_USER_REQUEST`를 반환한다.

같은 핸들러에서 본문을 읽지 못한 경우(`MALFORMED_REQUEST`) `fieldErrors`가 항상 `body`였다. 열거형에 없는 값처럼 어느 필드가 잘못됐는지 알 수 있으면 그 필드와 쓸 수 있는 값을 알려주도록 고쳤다.

```json
{ "field": "mediaList.mediaType", "message": "값 \"GIF\" 을(를) 쓸 수 없습니다. 가능한 값: IMAGE, VIDEO" }
```

### 미구현

- 이미지·영상 업로드: 저장소와 API가 정해지지 않았다. 현재는 클라이언트가 올린 URL만 받는다.
- 사진 EXIF 좌표 추출: 클라이언트가 좌표를 직접 넘긴다.
- 신고 처리 관리자 기능.

### 카테고리 목록 API 를 추가했다

`GET /api/v1/categories` 다. 쓸 수 있는 카테고리 전체를 등록 순서로 반환한다. 프론트가 카테고리 탭을 코드에 박아 두고 있었는데, 서버에서 받으면 탭이 늘거나 이름이 바뀔 때 프론트 배포 없이 반영된다.

사용 수로 정렬하지 않는다. 글이 쌓일 때마다 탭 순서가 바뀌면 사용자가 늘 같은 자리에서 같은 탭을 누를 수 없다. 자동완성(`/categories/search`)은 반대로 사용 수 순이다. 고르는 화면과 탭은 목적이 다르다.

### 장소를 사진에 붙인다

장소 태그를 게시물이 아니라 사진 단위로 저장하도록 바꿨다. 사진마다 다른 곳을 다녀왔을 수 있는데 게시물로 묶으면 어느 사진이 어느 장소인지 알 수 없다.

- 요청에서 `placeTags` 를 없애고 `mediaList[].placeId` 로 받는다. 선택이며 사진마다 따로 정한다.
- 응답의 `mediaList[]` 에 `placeId`·`placeName` 이 붙는다. `placeTags` 는 게시물에 붙은 장소를 모아 그대로 준다.
- 사진을 교체하면 장소도 함께 지워진다. 장소가 사진에 딸려 있기 때문이다.
- `V16__drop_post_place_tag_coordinates.sql` 로 `media_id` 를 추가한다. 장소를 붙이지 않은 사진이 있을 수 있고 예전 데이터는 어느 사진의 것인지 되짚을 수 없어 nullable 이다.

**사진 EXIF 좌표 컬럼을 지웠다.** 사진에서 GPS 를 읽어 장소를 추천하려던 계획이 바뀌어, 사용자가 자기 일정에 담긴 장소에서 고르거나 지도에서 검색하는 방식이 됐다. 좌표를 받을 경로가 없어졌고 장소의 대표 좌표는 `places` 에 있어 지도 표시에도 지장이 없다.

**장소 집계 조건을 고쳤다.** "장소 태그가 한 건인 글"에서 "서로 다른 장소가 한 곳인 글"로 바꿨다. 같은 장소를 사진 여러 장에 붙이면 행이 여러 개가 되는데, 전과 같은 조건이면 가리키는 곳이 하나인데도 집계에서 빠진다.

### 해시태그를 카테고리로 바꿨다

본문에서 `#태그` 를 뽑던 것을 없애고, 사용자가 목록에서 고른 값을 받는 방식으로 바꿨다.

- 요청·응답 필드가 `hashtags` → `categories` 다. 요청에 `categories` 를 새로 받는다.
- 조회 파라미터가 `?hashtag=` → `?category=` 다.
- 엔드포인트가 `/api/v1/hashtags` → `/api/v1/categories` 다.
- 본문의 `#맛집` 은 무시한다. 두 경로를 함께 두면 같은 글이 어떤 화면에서는 잡히고 어떤 화면에서는 빠진다.
- 본문 파싱이 사라져 `HashtagExtractor` 와 그 테스트를 지웠다.

**소프트 삭제에서 연결 행을 지우지 않도록 바꿨다.** 본문에서 뽑던 시절에는 삭제 때 연결을 끊어도 복구할 때 본문에서 다시 뽑으면 됐지만, 이제 카테고리는 본문과 무관해 연결을 지우면 무엇을 골랐는지 되짚을 근거가 사라진다. 삭제 시에는 사용 수만 줄이고 연결은 남기며, 완전 삭제에서 함께 지운다. 삭제된 게시물은 조회 쿼리가 걸러 내므로 목록·집계에는 나오지 않는다.

**DB 테이블 이름은 `hashtags`·`post_hashtags` 그대로 두었다.** 관리자 통계가 이 테이블을 직접 조회하고 있어 이름을 바꾸면 그 코드가 깨진다. API 가 보는 이름만 카테고리로 맞췄다.

### 등록된 해시태그만 붙는다

사용자가 새 태그를 만들 수 없게 바꿨다. 미리 등록해 둔 목록에 있는 태그만 게시물에 붙고, 목록에 없는 태그는 무시한다. 자유 태그가 아니라 우리가 정한 카테고리에서 고르는 방식이다.

쓸 수 있는 태그는 여덟 개이며 화면의 카테고리 탭과 같다.

```
맛집  카페  힐링  액티비티  쇼핑  야경  역사  자연
```

전에는 지역·성격·조합까지 39개를 등록해 두었으나, 카테고리로 쓰기로 하면서 탭에 있는 것만 남겼다.

자유 입력을 허용하면 같은 뜻의 태그가 표기만 달리해 흩어진다(`#부산맛집`, `#부산맛집추천`, `#부산맛집투어`). 그러면 태그로 거르는 화면이 제 구실을 못 한다.

**요청을 거절하지는 않는다.** 목록에 없는 태그를 써도 글은 그대로 저장되고 그 태그만 버린다. 오타 하나로 글 작성 자체가 막히면 안 되고, 태그는 분류를 돕는 값이지 글의 필수 조건이 아니다. 무시된 태그는 응답 `hashtags` 에도 담기지 않아 클라이언트가 결과를 확인할 수 있다.

쓸 수 있는 목록은 `GET /api/v1/hashtags/search` 로 조회한다. 클라이언트는 자유 입력 대신 이 목록에서 고르게 하는 것이 맞다.

태그를 새로 만들던 `HashtagRepository.insertIfAbsent` 와 그 동시성 테스트는 쓰이지 않게 되어 지웠다. 시드는 `HashtagSeedInitializer` 가 기동할 때 직접 넣는다.

### 카테고리 탭을 해시태그로 처리한다

화면의 카테고리 탭(`맛집`, `카페`, `힐링`, `액티비티`, `쇼핑`)에 대응하는 분류를 서버에 두지 않고 해시태그로 거른다. 탭 이름을 그대로 `hashtag` 파라미터로 넘기면 된다. 별도 컬럼이나 테이블을 만들지 않아도 되고, 탭이 늘어도 서버를 고칠 필요가 없다.

- **인기 피드에도 `hashtag` 를 받는다.** 최신 피드에만 있어서, 탭을 눌러도 인기 후기는 걸러지지 않고 전체가 그대로 나왔다. 한쪽만 걸리면 두 목록이 서로 어긋나 보인다.
- **시드를 탭 이름 여덟 개로 맞췄다.** 탭 이름 중 일부가 등록된 태그에 없어 자동완성에 뜨지 않았다.

### 해시태그가 가리키는 장소를 추가했다

`GET /api/v1/categories/{name}/places` 다. 이 태그가 달린 게시물들이 태그한 장소를 언급한 사람이 많은 순으로 준다. 태그를 눌렀을 때 글 목록 대신 지도를 보여주는 화면을 만들 수 있다.

관광 데이터에는 "현지인이 가는 곳" 같은 정보가 없다. 사용자가 붙인 태그로 그것을 만들어 내는 것이 목적이다.

해시태그는 장소가 아니라 글에 붙으므로 그대로 세면 어긋난다. 두 가지를 걸렀다.

- **장소를 하나만 태그한 게시물만 센다.** "해운대 갔다가 국밥집" 처럼 여러 곳을 태그한 글은 태그가 어디를 가리키는지 알 수 없어, 그대로 두면 해수욕장도 맛집이 된다.
- **서로 다른 사람 3명 이상이 언급한 장소만 반환한다.** 한 사람이 여러 번 태그해도 순위가 오르지 않고, 혼자 잘못 붙인 태그는 목록에 뜨지 않는다. **3명은 신뢰할 만한 기준이 아니라 데이터가 없어서 낮춰 둔 값이다.** 한 장소에 열 명이 같은 태그를 달려면 글이 수백 개는 쌓여야 하는데 지금은 그 기준으로 아무 장소도 뜨지 않는다. 글이 쌓이면 `COMMUNITY_HASHTAG_PLACE_MIN_AUTHORS` 를 올린다. 배포 없이 바꿀 수 있도록 설정으로 뺐다.

그래도 사용자가 만드는 데이터라 어긋난 태그가 섞일 수 있다. 확정된 분류가 아니라 사용자들이 붙인 태그임을 화면에서 알 수 있게 해야 한다. 장소 카테고리로 한 번 더 거르는 것(`#로컬맛집` 은 음식점만)은 태그별 카테고리 짝을 정해야 해서 후속으로 둔다.

**일정 생성 추천에는 넣지 않는다.** 일정 쪽 코드를 건드려야 하고, 커뮤니티 데이터가 일정 품질에 영향을 주는 것은 따로 논의할 일이다.

### 후속 수정

- **게시물 상세 응답의 `placeName` 과 미디어 `id` 가 문서에 나오지 않던 것을 고쳤다.** 요청용 `PostCreateRequest.PlaceTag` 와 응답용 `PostDetailResponse.PlaceTag` 가 이름이 같아 OpenAPI 스키마가 하나로 합쳐졌고, 요청용이 이기면서 응답에만 있는 `placeName` 이 문서에서 사라졌다. 실제 응답에는 처음부터 들어 있었으나 프론트가 Swagger 예시를 보고 없는 줄 알았다. 응답용 스키마 이름을 `PostPlaceTag`·`PostMedia` 로 분리했다.

같은 원인이 일정·장소 쪽에도 있다. `Stop`(응답 11개 필드 / 요청 4개), `OperatingInfo`(장소 상세의 `parkingText`·`useFeeText`), `Item`(장소 검색·위치 검색·주변 시설이 서로 덮음), `Location` 이 이름이 겹쳐 문서에서 필드가 빠진다. 팀원 담당 코드라 손대지 않았고 공유만 한다.

- **목록 API 의 `size` 상한을 검증한다.** 문서에는 "1 이상 50 이하"라고 적어 두고 상한을 확인하지 않아, 큰 값을 보내면 조용히 50으로 줄어 응답했다. 클라이언트는 요청한 만큼 못 받은 것인지 데이터가 없는 것인지 구분할 수 없다. 이제 `400` 을 반환한다. 커뮤니티 11곳이며 해시태그 자동완성만 상한이 30이다. 알림 목록은 검증이 아예 없어 함께 넣었다.
- **알림 저장을 별도 트랜잭션으로 분리했다.** 알림이 부르는 쪽과 같은 트랜잭션에서 돌아, 저장이 실패하면 팔로우나 댓글 작성까지 함께 롤백됐다. `NotificationWriter` 를 `REQUIRES_NEW` 로 두고 `NotificationService` 가 예외를 삼킨다. 예외를 잡는 자리가 트랜잭션 안이면 이미 롤백 표시가 붙어 커밋 시점에 다시 터지므로 빈을 나눴다.
- **`blocks` 에 역방향 인덱스를 추가했다.** `V15__add_blocks_reverse_index.sql`. 알림 조회와 댓글 작성이 차단을 양방향으로 확인하는데 기본키 `(blocker_id, blocked_id)` 로는 한 방향만 인덱스를 탄다.

### 재리뷰 지적을 반영했다

- **배포에 `COMMUNITY_POST_PURGE_ENABLED=true` 를 추가했다.** 기본값이 `false` 라 이 값이 없으면 정리 스케줄러 빈이 등록되지 않고, 기능을 다 만들어 놓고도 한 번도 돌지 않는 상태였다. 예전 `SCHEDULE_FASTAPI_ENABLED` 누락과 같은 형태다.
- **정리가 100건에서 멈추던 것을 고쳤다.** 한 묶음만 지우고 끝나 하루 만료량이 100건을 넘으면 매일 밀린 양이 늘어났고, 로그에는 "정리를 마쳤다"로 찍혀 알아채기 어려웠다. 트랜잭션은 묶음 단위로 짧게 두고 스케줄러가 남은 분량이 없을 때까지 반복한다. 무한 반복을 막는 상한(100묶음)을 두고, 상한까지 갔으면 경고 로그를 남긴다.
- **해시태그 연결도 `on conflict do nothing` 으로 바꿨다.** 좋아요·팔로우·저장만 바꾸고 여기가 남아 있어, 복구나 저장을 동시에 두 번 하면 기본키 충돌로 `500` 이 났다. 실제로 새로 연결된 것만 사용 수를 올리므로 두 번 저장해도 수가 두 번 오르지 않는다.
- **완전 삭제가 해시태그 사용 수를 되돌리도록 고쳤다.** 링크만 지우고 `hashtags.post_count` 를 그대로 두면 자동완성 정렬이 틀어지고 되돌릴 근거도 없다.
- **중복 신고가 `500` 이 되던 것을 고쳤다.** `V11` 로 고유 제약을 걸었는데 서비스는 확인 후 저장 구조 그대로였다. 확인과 저장 사이에 같은 신고가 들어오면 제약에 걸려 `500` 이 나갔다. 이제 제약 위반을 `409 ALREADY_REPORTED` 로 돌려준다.

- **새 해시태그를 동시에 처음 쓰면 `500` 이 나던 것을 고쳤다.** 같은 태그를 두 사람이 동시에 쓰면 양쪽 다 없다고 읽어 한쪽이 이름 고유 제약에 걸렸다. 확인 후 저장하지 않고 DB 에 맡긴 뒤 다시 읽는다. 미리 넣어 둔 인기 태그 36개로 확률을 낮춰 두었을 뿐 남아 있던 결함이다.

함께 발견해 고친 것이다.

- **행동한 사람이 없는 알림이 목록에서 통째로 빠졌다.** `notification.actor.deletedAt` 을 바로 타고 들어가 내부 조인이 걸린 탓이다. `left join` 을 명시했다. 시스템 알림이 아직 없어 드러나지 않았을 뿐 처음부터 있던 결함이다.
- **차단 관계인 사람의 알림이 계속 보였다.** 어느 쪽이 차단했든 목록과 `unreadCount` 에서 빠지도록 했다.
- **댓글 수정이 DB 에 저장되지 않았다.** `@Transactional` 이 빠져 있어 준영속 엔티티를 고치고 있었고, 응답은 메모리 객체를 그대로 돌려주므로 성공한 것처럼 보였다. 트랜잭션 없이 도는 테스트를 함께 추가했다. 테스트에 `@Transactional` 을 붙이면 서비스가 그 트랜잭션에 얹혀 가 이 결함을 잡지 못한다.

### 댓글 수정을 추가했다

`PATCH /api/v1/posts/{postId}/comments/{commentId}`다. 작성·삭제만 있고 고칠 수단이 없었다. 내용만 바꾸고 좋아요 수와 답글 관계는 그대로 둔다. 작성자 본인이 아니면 `403 COMMENT_ACCESS_DENIED`다.

### 알림을 추가했다

`GET /api/v1/notifications`, `GET /notifications/unread-count`, `PATCH /notifications/{id}/read`, `PATCH /notifications/read-all` 네 개다. `V14__create_notifications_table.sql`로 `notifications` 테이블과 인덱스 둘을 추가한다.

**알림은 커뮤니티 전용이 아니라 독립 도메인으로 두었다.** 알림 도메인은 누가 부르는지 모르고 받는 사람·종류·대상만 받아 쌓는다. 커뮤니티가 좋아요·댓글·답글·댓글 좋아요·팔로우 다섯 가지를 부르며, 나중에 일정처럼 다른 도메인에서 필요해지면 같은 방식으로 부르면 된다. `type`이 문자열이라 새 종류를 더할 때 마이그레이션도 필요 없다.

화면 문구는 클라이언트가 만든다. 서버는 `type`과 `actor`만 준다.

알림이 생기지 않는 경우는 내가 한 행동, 이미 눌러 둔 좋아요를 취소했다 다시 누른 경우, 받는 사람이 탈퇴한 경우다. 행동한 사람이 나중에 탈퇴하면 보여줄 이름이 없어 목록에서 빠진다.

남의 알림을 읽으려 하면 `404 NOTIFICATION_NOT_FOUND`다. `403`을 주면 그 알림이 있다는 사실이 드러난다.

**새 알림은 클라이언트가 주기적으로 조회해 받는다.** `GET /notifications/unread-count`를 30초 간격 정도로 부르면 벨 표시가 갱신되며, 서버는 이 방식에 필요한 것을 모두 갖췄다. 서버가 밀어 보내는 방식(SSE)이나 브라우저 알림(Web Push)은 쓰지 않는다. 전자는 접속자 수만큼 연결을 유지해야 하고 후자는 서비스 워커·HTTPS·권한 요청에 iOS 홈 화면 추가까지 필요한데, 알림이 몇십 초 늦게 뜨는 것은 문제가 되지 않는다.

### 게시물 수정이 사진과 장소 태그도 바꾼다

`PATCH /api/v1/posts/{postId}`가 본문만 바꾸던 것을 `mediaList`, `placeTags`까지 받도록 넓혔다. **보낸 항목만 바뀌고 생략한 항목은 그대로 둔다.** 배열을 보내면 통째로 교체하므로 사진 한 장을 빼려면 남길 사진들을 보낸다. 추가·삭제·순서 변경이 같은 방식이라 별도 파라미터를 두지 않았다.

`mediaList`는 빈 배열로 보낼 수 없다. `placeTags`는 빈 배열이면 모두 없앤다. 세 항목을 모두 생략하면 `400 INVALID_POST_REQUEST`다.

호환성은 유지된다. `content`만 보내던 기존 요청은 그대로 동작한다.

**교체로 빠진 사진의 실제 파일은 지우지 않는다.** 저장소가 정해지지 않아 지울 수단이 없다. 저장소를 붙일 때 남은 파일 정리가 함께 필요하다.

### 게시물 복구를 추가했다

`GET /api/v1/posts/me/deleted`와 `POST /api/v1/posts/{postId}/restore`다. 소프트 삭제만 있고 되살리는 수단이 없어 기획의 "30일간 복구"가 사실상 동작하지 않았다. 복구할 때 본문에서 해시태그를 다시 뽑아 연결하므로, 삭제 시 연결을 물리 삭제하던 것과 짝이 맞는다.

기한이 지난 게시물은 매일 04:30(KST) 스케줄러가 실제로 지운다. 게시물과 함께 미디어·장소 태그·댓글·댓글 좋아요·좋아요·저장·해시태그 연결을 지우며, 외래키 때문에 참조하는 행부터 순서대로 지운다. 실행 여부와 보관 기간은 `app.community.post-purge`(`COMMUNITY_POST_PURGE_ENABLED`, `COMMUNITY_POST_RETENTION_DAYS`, `COMMUNITY_POST_PURGE_CRON`)로 바꾼다. **배포 환경에서 켜지 않으면 지운 게시물이 계속 쌓인다.**

복구 기한과 보관 기간은 같은 설정값을 쓴다. 복구 기한이 더 길면 아직 되돌릴 수 있는 글이 먼저 지워진다.

**계정 탈퇴는 되돌릴 수 없다.** 되살릴 수 있는 것은 본인이 지운 게시물뿐이며, 탈퇴한 사용자의 게시물은 복구 대상이 아니다.
